# R5 model A/B: bounded 16 GiB retry

## Question and authorized change

Can the unchanged R5 diagnostic model A/B finish after tmpfs retirement and
raising only the verification container's RAM limit from 12 to 16 GiB?
The user authorized this retry on 2026-09-14. Swap remains disabled for this
container; no automatic limit escalation is permitted.

Starting commit: `5960476cd7f2dc697c4ce2b3c8e234acb2b75bf9`, isolated worktree
`/tmp/vllm-tq-prefill-r5`, branch `codex/gfx1201-prefill-r5`. The original
checkout's user changes are not part of this experiment.

The earlier strict Math diagnostic and the 12 GiB startup OOM remain historical
results in the [previous report](gfx1201_prefill_rearchitecture_r5_speed_20260914.md).
No kernel, production dispatch, cache format, numerical gate, or model option
was changed. Only the benchmark launcher resource guard changes to 16 GiB.
The existing model environment and pinned AMD backend are retained.

## Memory preparation and startup

Old benchmark SDK/development directories and the Radiance control cache were
copied out of host tmpfs into `/srv/ai/tmp-retired-20260914`, checked for content
equality, and replaced by symlinks. Their contents were not discarded. Host
`/tmp` usage fell from approximately 11 GiB to 1 GiB. R5's container-local
`/dev/shm` caches were retained. No swap reset or global cache drop was used.

The launcher uses Runai streaming with a 3 GiB loader memory limit. That is
not an overall process or container memory cap. The prior 12 GiB OOM snapshot
contained about 10.14 GiB anonymous memory, 1.79 GiB shmem and 0.08 GiB kernel
memory; ordinary file cache was almost entirely reclaimed.

The 16 GiB retry completed both target and MTP loading. The logged 18.7 GiB
model allocation is GPU memory, not host RAM. Host memory was monitored at
roughly ten-second intervals, independently of the inference profiler.
The profiler was never started. Historical cgroup counters are cumulative:
`oom=6`, `oom_kill=9` at retry start, not new failures in this run.

## Measurement contract

The existing fixed token-ID prompt, cold prefix salts, chunk budget 256,
TP1, K8/V4, MTP2, disabled adaptive verification, validated fused MXFP4 decode,
compilation mode 0 and FULL_DECODE_ONLY are unchanged. There is one server
load for both arms. Both 4K smoke requests completed with 64 tokens, 16 target
attention layers and 240 eligible continuation calls. Only the candidate arm
applied the upstream backend.

Both arms run one untimed cold32K warmup, then five measured pairs with order
B/C, C/B, B/C, C/B, B/C. Every request ignores EOS and generates 64 tokens.
The executed container runner predates the repository runner's suite-ID salt
prefix: it uses `warmup-baseline`, `sample0-baseline`, etc. All request salts
are unique within this fresh server; the actual runner is preserved with the
artifacts. The client, hook and sitecustomize hashes match the checked-in code.

Warmup TTFT was 133.739990 s for baseline and 325.894630 s for candidate.
These are excluded from the gate. The much shorter subsequent candidate
latency demonstrates a large first-execution effect; it does not alone
attribute every extra second to a particular compiler or kernel.

## Results

**Model TTFT passed; quality and operational evaluation pending.**

| 0 | B/C | 132.400164 | 60.656275 |

| 2 | B/C | 131.825731 | 60.609778 |

| 4 | B/C | 131.771033 | 60.615601 |
| Median | | **131.796047** | **60.643420** |

Reduction: **53.9869%**, speedup **2.1733x**. The unchanged 10% TTFT reduction
gate passes. All ten measured requests completed 64 tokens without stream
errors. Every request records 1,984 eligible continuation calls across the
same 16 target attention layers; applied calls are 0 for baseline and 1,984
for candidate. Prefix hit counters remain zero. Token IDs are stable within
each arm but differ at 45 of 64 positions between arms. This is recorded, not
treated as a task-quality verdict.

Both arms report process-lifetime GPU allocator peaks of 32,372,646,912 bytes
allocated and 33,403,437,056 bytes reserved after warmup. These include startup
and preceding requests; they are not per-arm incremental memory measurements.

The maximum sampled container RAM usage was about 15.900 GiB. Samples are not
an exact high-water mark; the kernel's historical `memory.peak` was not reset
and is not used. There is a monitoring gap from 10:23:28 to 10:24:46 UTC; raw
timestamps are retained. The start/end OOM counters are unchanged (`oom=6`,
`oom_kill=9`). The initial cgroup limit-hit counter grew during loading as
cache was reclaimed, without an OOM. The diagnostic API and engine were
stopped normally after measurement; host available RAM returned to about
21 GiB. Container RAM remains capped at 16 GiB with swap disabled.

This establishes that this configuration can load and complete cold32K on
the current 32 GB host after tmpfs retirement and the bounded limit change.
It does not establish a minimum RAM requirement or guarantee that every
16 GiB loading environment will succeed.
