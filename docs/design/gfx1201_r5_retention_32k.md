# R5 32K content-retention diagnostic — preparation

This is an independent long-context retrieval diagnostic. It does not make the
previous R5 supplemental quality evaluation pass, does not rewrite its stop,
and does not authorize production adoption. The previously recorded cold-32K
TTFT improvement of 2.1733x, GSM8K score decrease, HumanEval truncation
increase, and completed-pair format item passing remain unchanged.

## Frozen fixture

Preparation starts at commit `328c415d596b64e9d4d6b094a642c6540e813021` on
`codex/gfx1201-prefill-r5`. The suite has three fixed registry documents and
three fixed insertion positions (early, middle, late), for nine cases total.
Each case contains one answer-bearing registry sentence and a final question
that repeats only the identifier. The answer is not present in the filler or
question. The complete non-thinking chat-template prompt, document, and
question are exactly 32,768 token IDs. Sentence and target boundaries are
preserved; the manifest records absolute token positions.

The suite and manifest are generated by
`benchmarks/r5_quality/build_retention_suite.py`. CPU construction checks verify
the exact target length, unique answer, absence of other answers, prompt
round-trip, and baseline/candidate token-ID identity. The preparation manifest
also fixes the tokenizer file hashes, sampling, output limit, template flags,
cache isolation rule, and scoring contract before any response is generated.

The main score is exact equality after removing only leading and trailing
whitespace. Contains-answer, empty, finish reason, and output length are
recorded separately. No answer repair, completion, normalization, retry, or
fixture adjustment is permitted.

## Fixed execution

Both arms use the existing diagnostic hook and only the existing target
continuation attention consumer. No kernel, input contract, KV layout, MTP,
decode path, production dispatch, or default is changed. The environment is
TP1, TurboQuant K8/V4, MTP2, adaptive verification disabled, fused MXFP4
decode enabled, compilation mode 0, `FULL_DECODE_ONLY`, chunk budget 256,
`max_num_seqs=1`, temperature 0, seed 1201, normal EOS handling, and
`max_tokens=128`.

One model process executes the nine cases sequentially, alternating B/C and
C/B order. Each arm/case has a unique cache salt; no prefix cache is shared
between arms or placement variants. A separate fixed warmup is allowed only
if needed and is not scored. The runner records raw answers and token IDs,
finish reason, timing, hook shape/layer/application counts, cache/MTP metrics,
and bounded RAM/VRAM/OOM observations. A short final continuation remains on
its existing dispatch; it is never forced into the candidate.

The run is bounded to 16 GiB RAM with swap disabled, uses no profiler, and
writes artifacts to disk rather than accumulating them in tmpfs. New OOM,
generation error, non-finite result, server stop, or stalled request stops the
run without automatic retry.

## Result boundary

The paired table reports both-correct, baseline-only, candidate-only, and
both-incorrect cases overall and by early/middle/late placement. Candidate
coverage and target overlap are separate validity checks. Even a 9/9 result
means only that this fixed nine-case 32K information-retrieval diagnostic
succeeded. It does not establish general long-context quality, reverse the
previous supplemental quality failure, or approve production use.

Decode regression, prefix reuse, soak, 64K/120K, further kernel work, and
production integration are outside this run. A later result section will be
added in a separate commit after the one-pass measurement.
